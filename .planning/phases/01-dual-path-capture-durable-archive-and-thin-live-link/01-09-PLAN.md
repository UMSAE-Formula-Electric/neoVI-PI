Written in `tests/test_hardware_source.py`, replacing 01-02's placeholder skip. Every test
drives an injected fake SDK object, never the real `ics` module, so the suite is identical on
a laptop and on the CM4.

Channel resolution:
- each configured channel's symbolic net-ID constant name resolves against the SDK object and
  produces the integer the fake exposes
- a configured symbolic name the SDK object does not expose raises a named error at
  construction, naming the channel and the symbolic constant it could not find, and no
  partially-constructed source is returned
- resolving produces a net-ID-to-channel-name map covering exactly the configured channels
- one test, skipped if the real `ics` module cannot be imported, asserts that every symbolic
  name in the shipped `config/logger.json` resolves against the real module — so a config
  naming a constant that does not exist in the installed SDK is caught by the suite rather
  than at first boot on the car

Device open:
- with a fake reporting no devices, opening raises a named error whose message says no device
  was found, and does so without retrying or blocking
- with a fake reporting several devices and a configured serial, the matching device is
  selected; with a configured serial that matches none, the error names the configured serial
  and lists what was available
- with a fake reporting several devices and no configured serial, the first is selected

Isolation from the legacy SDK:
- assert that `telemetry.capture.hardware_source` does not import `vspyx`, directly or
  transitively, and that no module under `telemetry` does. The test docstring records why:
  the research session observed a bare import of that package hang for thirty seconds with no
  hardware present, and an unattended logger that hangs at boot never recovers on its own
  </behavior>
  <action>
Create `src/telemetry/capture/hardware_source.py`. Take the SDK module as an injectable
constructor argument defaulting to the real `ics` module, imported lazily inside the default
factory rather than at module import time. That one seam is what makes every test in this
plan runnable with no driver, and it costs nothing at runtime.

Resolve channels from config, not from source. `src/new_logger.py` hardcodes a channel map at
lines 41 to 59; `01-CONTEXT.md`'s locked decision extends "never baked into code" from the
allowlist to this map as well. For each configured channel, look up its symbolic constant name
on the SDK object and raise a named error if it is absent. Do not reproduce
`resolve_net_ids`'s behaviour at line 131, which logs a warning for an unrecognised channel
and then continues with no filtering at all — a config naming a bus that does not exist would
then silently capture everything, which is both wrong and invisible. Here it stops startup.

Build the device-open path from `src/new_logger.py` lines 96 to 118: enumerate devices, select
by configured serial or take the first, open it. Keep its fail-fast raise with a descriptive
message, and add what CAP-06 requires on top — log the failure with the configured serial and
the list of devices actually seen before raising, so a bench diagnosis does not require
re-running under a debugger.

Store a net-ID-to-channel-name map built from config, so a captured message can be tagged with
the friendly channel name the archive and the dashboard use.

State in the module docstring that this module is the consolidated capture implementation for
CAP-01's first clause, that the SDK choice rests on directly observed hardware-free behaviour
recorded in `01-RESEARCH.md` Pattern 5, and that no module under `telemetry` may import the
legacy SDK — including through a fallback path, because a "try the other SDK" branch would
reintroduce exactly the boot-time hang the choice avoids.

  <name>Task 2: The poll loop, frame construction, and hardware error accounting</name>
  <files>src/telemetry/capture/hardware_source.py, tests/test_hardware_source.py</files>

  <behavior>
Added to `tests/test_hardware_source.py`, all against the fake SDK:

- `captured_frames()` yields one `CapturedFrame` per SDK message, with the channel name
  matching the message's net ID, the arbitration id masked to 29 bits, the extended flag taken
  from whatever field the probe below establishes as authoritative, the payload sliced to the
  reported byte count, and the timestamp converted to microseconds by the documented constant
- messages whose net ID is not one of the configured channels are excluded, and the count of
  excluded messages is available on the counters object rather than being invisible
- `frames()` yields the same frames as `RawFrame`s, satisfying the existing `FrameSource`
  protocol, so the Phase 0 measurement tooling can consume this source with no change
- a non-zero hardware error count reported by the SDK increments a hardware-error counter and
  emits a log record carrying the poll iteration and the count
- an exception raised by the SDK's message-poll call is caught by its own type, logged at
  critical severity with the poll iteration attached, recorded on the counters, and then
  re-raised after the stop event is set — never reduced to a debug-level message the way the
  legacy loop does
- the loop exits promptly when the stop event is set, without waiting out a full poll interval
- with the fake producing messages on both configured net IDs interleaved, both channels
  appear in one stream from one source instance — CAP-01's first clause at the source layer
  </behavior>
  <action>
Before writing the frame-construction code, establish three SDK facts from the installed
module rather than from memory or from `src/new_logger.py`'s usage, and record each one and
how it was established in the SUMMARY:

1. Which message attribute carries the extended-identifier flag. `src/new_logger.py` masks the
   arbitration id to 29 bits and never records whether a frame was extended, so it is not a
   source of truth here — but `RawFrame`'s `is_extended` is load-bearing, because the ID
   dictionary is keyed on the `(frame_id, is_extended)` pair and several messages in this DBC
   carry the extended marker. Inspect the installed module's own constants and message
   attributes to find the authoritative flag.
2. The unit and epoch of the timestamp field. `RawFrame.timestamp_us` is microseconds; the SDK
   field's unit must be established, not assumed, and the conversion expressed as a named
   module constant with a comment recording how the unit was determined.
3. The exact call signature and return shape of the message-poll function, so the error-count
   value is read from the right position.

If any of the three cannot be established with confidence from the installed module, do not
guess a value into the code. Implement the conversion behind a named constant, mark it clearly
as unconfirmed in both the constant's comment and the SUMMARY, and add it to the hardware
bring-up checks below so the first bench session settles it. `01-RESEARCH.md` Assumption A2
already flags timestamp semantics as an untested area; carrying an assumption forward as a
labelled assumption is correct, promoting one to a fact is not.

Then write the poll loop, taking the reusable shape from `src/new_logger.py` lines 164 to 211
and none of its error handling: poll at the configured interval, filter by the resolved net-ID
set, construct one `CapturedFrame` per surviving message, and check the stop event every
iteration. Keep the SDK's own reported error count wired to a counter, as the legacy loop
does, and add the logging with context that it lacks.

Expose `captured_frames()` as the primary generator and `frames()` as a thin delegate that
yields only the `RawFrame` half, documenting that the delegate exists to satisfy the
`FrameSource` protocol and deliberately discards the channel tag.
  </action>
