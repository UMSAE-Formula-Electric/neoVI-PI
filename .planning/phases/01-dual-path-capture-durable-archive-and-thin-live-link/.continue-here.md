<decisions_made>

- **Bus split uses the real D-03 rate model, not an artificial alternation.** Each
  synthetic frame's channel is resolved via `{(r.frame_id, r.is_extended):
  bus_to_channel[r.bus] for r in source.rates}` — `source.rates`'s `.bus` field
  ("bus1"/"bus2") is mapped through `logger_config.channels`' own `.bus` field
  (MAIN→bus1, SENSOR→bus2 per `config/logger.json`). This is more faithful to
  "genuinely combined bus load" than `test_dual_bus_capture`'s `i % 2` alternation,
  since it's the SAME assignment the rate model used to hit
  `config/gate.json`'s per-bus `target_fps`.

- **[Rule 1 — Bug] The plan's literal accounting equation double-counts; implemented
  the actual conservation identity instead.** Plan text (Task 1 action) says: "the
  telemetry path's discard count plus its enqueued count plus its allowlist-filtered
  count equals the total frames submitted." Traced through `telemetry/capture/
  fanout.py`'s actual `submit()`: `telemetry_enqueued` increments unconditionally on
  every successful `deque.append()`, INCLUDING appends that evict an older,
  already-counted entry (`deque(maxlen=N)`'s drop-oldest auto-eviction, tracked
  separately as a flag on that SAME append event, not a disjoint bucket, via
  `telemetry_discard_count`). Summing discard+enqueued+filtered therefore
  double-counts by exactly `telemetry_discard_count` whenever it's nonzero — the
  identity as literally stated only holds when discard==0, which contradicts
  critical constraint 5 (telemetry-path drops are EXPECTED, not a failure; must
  never be asserted to zero). Implemented instead the identity that IS exactly true
  by construction regardless of discard: `frames_submitted == telemetry_filtered_count
  + telemetry_unknown_id_count + telemetry_payload_too_long_count +
  telemetry_unexpected_error_count + telemetry_enqueued` (every submitted frame
  falls into exactly one of these five buckets in `submit()`'s control flow).
  `telemetry_discard_count` is reported as a plain number (observed 107 in the
  first passing run) and never asserted to any specific value. **Document this
  explicitly in the SUMMARY's Deviations section when writing it** — this is a
  Rule 1 auto-fix (bug in the plan's own arithmetic), not a scope change.

- **Wall-clock window for achieved_fps** spans from immediately before the
  submission loop starts through `archive_runner.join()` returning (archive path
  fully drained) — deliberately EXCLUDES `writer.close()`'s one-time MCAP
  footer-finalize cost, since that's a fixed per-session closing cost, not part of
  the repeating per-frame throughput the "sustained rate" claim is about.

- **Combined target fps is read from `config/gate.json`'s `bus_targets`**
  (`sum(bt.target_fps for bt in gate_config.bus_targets.values())` = 2900 + 830 =
  3730.0), never a hardcoded "~4000" literal — Phase 0's own recorded lesson about
  prose figures drifting from the config that actually produced them.

- **All per-stage timing instrumentation lives in the test file only**, by wrapping
  bound methods (`writer._flush_and_sync`, `encoder.encode`, `link.send`) and
  monkeypatching module-level functions (`pipeline_module.pack_batch`,
  `pipeline_module.cobs_frame`) — no production module is touched. This matches
  `tests/test_archive_writer.py`'s existing convention of assigning directly to
  `writer._fsync` for the same purpose, so it's not a new pattern for this repo.
