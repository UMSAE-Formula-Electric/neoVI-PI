<decisions_made>

Full rationale for each of these is in `.planning/HANDOFF.json`'s `decisions` array — summarized here:

- **Extended-ID flag — ESTABLISHED.** Use `StatusBitField & ics.SPY_STATUS_XTD_FRAME` (`0x4`), not
  `ics.SPY_STATUS_EXTENDED` (`0x80000000`). `XTD_FRAME` sits in the coherent low-order per-frame flag
  family (`GLOBAL_ERR=0x1, TX_MSG=0x2, XTD_FRAME=0x4, REMOTE_FRAME=0x8, CRC_ERROR=0x10`);
  `SPY_STATUS_EXTENDED` sits in a separate high-bit tier that even reuses `0x20000000` for both
  `CANFD` and `INIT_MESSAGE` (overloaded, unreliable as a simple per-frame flag). Corroborated by
  `src/new_logger.py`'s existing TX code, which already sets
  `msg.StatusBitField = ics.SPY_STATUS_XTD_FRAME` to mark an outgoing frame extended on the exact
  same field.
- **Poll return shape — ESTABLISHED.** `ics.get_messages(device)` returns
  `(tuple_of_SpyMessage, error_count)` — confirmed verbatim from the installed module's own
  docstring/example, matching `new_logger.py`'s existing `msgs, error_count = ics.get_messages(device)`.
- **Timestamp unit/epoch — NOT ESTABLISHED, deliberately left unconfirmed.** `SpyMessage.TimeSystem`'s
  docstring (captured live via `help(ics.SpyMessage)`) says it comes from the Windows-only
  `timeGetTime()` API — milliseconds, arbitrary uptime-relative epoch — but the deployment target is
  Linux (CM4), so this Windows-specific text may not describe what the same attribute reports on real
  hardware. `new_logger.py`'s existing `%.6f`-seconds CSV formatting is not authoritative counter-
  evidence (an integer-millisecond value formatted with 6 decimals just shows trailing zeros). A
  second candidate, `ics.get_timestamp_for_msg(device, msg)`, returns a bare `Float` with no
  documented unit/epoch at all. `01-RESEARCH.md` Assumption A2 already flagged this exact gap.
  Implement behind a named, explicitly-UNCONFIRMED constant; do not resolve by picking one and
  moving on.
- **`ics.RuntimeError` is not `builtins.RuntimeError`.** Verified live:
  `issubclass(ics.RuntimeError, RuntimeError)` is `False`; its MRO is
  `(ics.ics.RuntimeError, Exception, BaseException, object)`. Confirmed as the actual type raised in
  this dev environment — `ics.find_devices()` with no driver raised
  `ics.ics.RuntimeError: Error: find_devices(): Failed to Retrieve address of function
  'icsneoFindDevices': Windows Error #127 for library 'icsneo40.dll'`. Catch via the injected SDK
  object's own exception class, never the bare builtin.
</decisions_made>
