<objective>
Turn the tracer's archive writer into the thing ARCH-01 and ARCH-04 actually claim: every
frame written, flushed on a batched count-or-time cadence, and structurally incapable of
stalling capture.

Purpose: the locked cadence — 1000 records or 250 ms, whichever comes first — cannot be
expressed through `mcap`'s own flush trigger at all, because `chunk_size` is a byte threshold.
`01-RESEARCH.md` Pitfall 2 records the consequence of not noticing that: with the library's
default chunking, up to a megabyte of messages sit in process memory before a single byte
reaches the stream, and at raw-CAN record sizes that is tens of thousands of frames of
silent, unrecoverable exposure. The cadence is therefore this module's own concern, layered
on unchunked writes, with an explicit sync call the library never makes on its own.

Output: a writer whose durability behaviour is asserted rather than assumed, and a drain
thread that keeps flush latency off the capture path.
</objective>

Round-trip completeness (ARCH-01):
- write two hundred frames spread across both configured channel names, close, then read the
  file back through `recover_session`; assert the recovered count equals two hundred and each
  recovered frame's id, extended flag, payload, and timestamp match what was written
- assert frames written under two different channel names come back tagged with two distinct
  topics, and that a frame's topic matches the channel it was submitted on

Cadence, with the sync function patched and its calls counted (ARCH-04):
- with `flush_every_records` set to ten and `flush_every_s` set high enough never to fire,
  writing one hundred records produces exactly ten syncs before close
- with `flush_every_records` set high enough never to fire, an injected clock advanced past
  `flush_every_s` between writes produces one sync per elapsed window
- with both cadences able to fire, the count trigger firing first does not also produce a
  redundant time-triggered sync in the same window — the elapsed timer resets on every sync
- `close()` produces a final sync after `finish()` regardless of how many records are pending
- `writer.flush_count` and `writer.records_written` agree with the observed sync count and
  record count

The unchunked-write pin: after writing exactly one record and before calling `close()`,
assert the file on disk already has a non-zero size and that reading it back through
`recover_session` yields that one record. This is the regression guard for the library's
default chunking behaviour — under the default the file would still be effectively empty at
this point.

Sync is really called: assert that with the sync function patched to raise, `add` propagates
the failure rather than swallowing it. A silently no-op'd sync is the failure mode that would
make every other durability claim in this phase false while every test still passed.
  </behavior>
  <action>
Extend `src/telemetry/archive/writer.py`. Keep the tracer's `Writer(file_obj,
use_chunking=False)` construction and its file-object ownership exactly as they are — both
are load-bearing and verified.

Make the cadence explicit and inspectable: hold `flush_every_records` and `flush_every_s`,
track records since the last sync and the monotonic time of the last sync, and after each
`add` sync when either threshold is reached. Reset both trackers together on every sync so a
count-triggered sync also restarts the time window. Accept the monotonic clock as an
injectable callable so the time branch is testable without sleeping.

Resolve the platform sync function once at construction with `getattr(os, "fdatasync",
os.fsync)` and store it on the instance so tests can patch it. Record in the docstring that
the `fdatasync` branch is the one the CM4 uses and the one the Windows dev box can never
exercise — the dev suite only ever runs the `os.fsync` branch, and `docs/power-pull-test.md`
is where the Linux branch is actually proven.

Do not catch exceptions from flush or sync. An I/O failure on the durability path is exactly
the condition that must stop the session loudly; swallowing it would leave the logger
reporting healthy while writing nothing to the device.

Expose `records_written`, `flush_count`, and `is_closed` as read-only properties. `is_closed`
is what `mark_done` checks, so it must become true only after `finish()`, the final flush,
and the final sync have all returned.

  <behavior>
Added to `tests/test_archive_writer.py`:

- `ArchiveRunner` started against a `FanOut`'s archive queue drains every submitted frame into
  the writer, and after the sentinel is pushed and the thread joined, the archive holds every
  submitted frame with none missing and none duplicated
- ARCH-04's real claim: with the writer's sync function patched to sleep for a duration far
  longer than the producer's per-frame interval, a producer submitting a burst of frames sees
  its own per-submit call time stay bounded well under that sleep, and after the drain
  completes every frame is still in the archive. The flush cost lands on the queue, not on
  the producer.
- the runner exits cleanly on the sentinel, and separately exits on the stop event even with
  items still queued, draining what remains before returning
- the runner records the archive queue's high-water mark as it drains, and that value is
  visible on the shared counters object after the join
  </behavior>
  <action>
Create `src/telemetry/archive/runner.py` holding `ArchiveRunner`, the consumer end of the
fan-out's archive queue. Follow the thread discipline `01-PATTERNS.md` extracts from
`src/new_logger.py` and keep every part of it: name the thread for debugging, poll a shared
`threading.Event` every loop iteration, use a module-level sentinel object pushed onto the
queue to signal drain-and-stop, and make this thread non-daemon so it flushes before process
exit — the capture thread is the daemon, the writer never is.

The runner's loop takes from the archive queue with a short timeout, updates the archive
high-water mark on the shared counters object, hands the frame to `ArchiveWriter.add`, and
stops on either the sentinel or the stop event, draining whatever is still queued before
returning so a shutdown does not discard already-captured frames.

Do not copy `src/new_logger.py`'s error handling. Its capture loop catches bare `Exception`,
reports it only through a debug helper that is invisible unless a module flag is set, and
then exits. Here, an exception from the writer is logged at critical severity with the frame's
channel, id, and timestamp, recorded on the counters object, and re-raised after the stop
event is set, so a durability failure stops the session visibly rather than continuing to
accept frames it is no longer persisting.

Do not import anything from `telemetry.archive` inside `telemetry.capture.fanout`. The
one-directional dependency is what makes ARCH-04 and CAP-04 structural rather than a promise:
the producer holds a queue and nothing else.
  </action>
