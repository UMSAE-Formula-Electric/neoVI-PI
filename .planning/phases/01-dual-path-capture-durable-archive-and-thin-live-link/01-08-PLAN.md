<objective>
Prove the framing layer's two hard claims — resync after corruption, and discard-and-count
rather than pass-upstream — and add the second link implementation so LINK-03's swappability
is demonstrated rather than asserted.

Purpose: LINK-01 does not just say "use COBS and a CRC", it says a corrupted byte stream
resynchronizes at the next frame delimiter. That is a behavioural claim about what happens
after damage, and it is only true if the CRC lives inside the COBS envelope — which is the
correction the tracer made to `01-RESEARCH.md`'s sketch. This plan is where that claim gets
tested rather than reasoned about. UDP then supplies a real network hop with real packet
loss, while still needing no radio anywhere in the chain.

Output: the framing layer's failure behaviour pinned by test, and two interchangeable links.
</objective>

Written in `tests/test_framing.py`, replacing 01-02's placeholder skip. Use the session-scoped
`dbc` fixture and a real `IdDictionary` so the batches under test carry real CFR records
rather than invented bytes.

Round trip (LINK-01):
- a batch of one record, a batch of the configured batch size, and a batch of the largest
  size the header's frame_count field can express all frame and unframe to byte-identical
  payloads
- a batch whose payload contains zero bytes in the CFR records still produces framed output
  containing exactly one zero byte — the trailing delimiter — because that is the property
  delimiter-based resync depends on
- the framed size of a realistic batch matches what `wire/overhead.py` predicts for that
  clean payload size, within the one-byte-per-record difference the tracer documented; assert
  against the module's own functions, not against a copied number

Corruption discrimination (LINK-02):
- flipping a byte inside the CRC trailer region raises the CRC-mismatch error, not the COBS
  error
- flipping a byte in a way that breaks the COBS length chain raises the COBS error
- truncating a framed batch mid-record raises the batch-format error
- a batch whose frame_count disagrees with the number of records actually present raises the
  batch-format error
- for each of the three, the `Deframer` catches it, increments exactly the one matching
  counter, yields nothing for that segment, and does not raise
- for each of the three, assert that no decoded frame from the damaged batch is emitted:
  count what the deframer yields, not just what it counts

Resync (LINK-01's actual claim):
- concatenate three framed batches, corrupt the middle one's bytes, feed the whole stream to
  one `Deframer` in a single `feed` call: the first and third batches decode correctly, the
  middle is counted as corrupt, and the third's records decode to the right values — proving
  recovery resumed at a delimiter rather than the stream being poisoned
- feed the same three-batch stream in arbitrarily-sized chunks, including chunks that split a
  frame across a boundary, and assert the same result — the deframer is fed a byte stream,
  not tidy messages
- inject a run of random non-zero garbage between two valid frames and assert the following
  valid frame still decodes, with exactly one corruption counted
- feed a stream with no delimiter at all, longer than the configured maximum frame size, and
  assert the pending buffer is discarded, the event counted, and memory does not grow with
  continued feeding
  </behavior>

Written in `tests/test_link.py`, replacing 01-02's placeholder skip. Structure the file as one
suite parameterised over both link implementations, so LINK-03's "no change to the layers
above" is demonstrated by the same assertions passing against both rather than by two separate
test files that could quietly diverge.

Shared behaviour, run against both `LoopbackLink` and `UdpLink`:
- a payload sent is the payload received, byte-identical
- `recv` with a timeout and nothing to receive returns `None` rather than raising or blocking
  indefinitely
- `close` is idempotent, and `send` after `close` raises rather than silently discarding
- the full chain from `01-04`'s tracer — encode, batch, frame, send, receive, deframe, decode
  — produces the identical decoded frames over either link, asserted by comparing the two
  results to each other, not just each to a literal

UDP-specific:
- both ends bind to the loopback interface on an ephemeral port, and the receiving link's
  bound address is readable so the sending link can be pointed at it without a hardcoded port
- a datagram larger than the receiver's configured buffer is truncated by the socket layer
  with no error, and the deframer therefore counts it as corrupt and does not pass it
  upstream. Assert that outcome, and give the test a docstring stating why the shipped
  `recv_bufsize` is deliberately generous rather than tight: a legitimate frame truncated at
  the socket layer would otherwise inflate the corrupt-batch counter with events that were
  never link corruption, which would mislead the loss diagnostics Phase 5 builds on that
  counter
- send several batches and assert every one that arrives arrives intact; do not assert that
  none is lost, because UDP's own unacknowledged loss is a modelled feature of the real radio
  link and asserting delivery would make the suite flaky for the wrong reason

Radio-free (LINK-04): assert that neither implementation imports `serial` or any radio
driver, and that the whole suite runs with no vehicle hardware and no second machine — the
UDP path uses the loopback interface only.
  </behavior>
  <action>
Create `src/telemetry/link/udp.py` with `UdpLink`, built on `01-RESEARCH.md` Pattern 7's
reference implementation. It satisfies the `Link` Protocol from `link/base.py` and adds
nothing to it — the whole point of LINK-03 is that the layers above see three methods and
nothing more.

Bind one datagram socket to the configured local address. Expose the socket's actual bound
address as a read-only property, so an ephemeral port assignment is discoverable by the
caller; a test cannot otherwise wire two ends together without hardcoding a port, and the
ground station will want to log the port it is actually listening on.

`send` writes one datagram per call. `recv` sets the socket timeout and returns the received
bytes, or `None` on timeout — catch the timeout exception and return `None` rather than
letting it escape, because `None` on timeout is the Protocol's contract and every caller is
written against it. `close` closes the socket and is safe to call twice.

Size the receive buffer from config rather than a literal, and note in the docstring that
`recvfrom` silently truncates a datagram larger than its buffer with no error raised, which
is why the shipped value is generous rather than tight.

Phase 1 sends one datagram per batch and does not coalesce. `01-RESEARCH.md` Pattern 6
computed, using this repository's own overhead module, that every plausible Phase 1 batch size
sits well under the practical Ethernet and Wi-Fi UDP payload ceiling, so fragmentation is not
a concern at this phase's sizes and no special handling is needed. Do not add coalescing on
speculation.
  </action>
