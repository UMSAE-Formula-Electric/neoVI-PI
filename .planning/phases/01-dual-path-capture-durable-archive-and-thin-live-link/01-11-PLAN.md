  <behavior>
Added to `tests/test_end_to_end.py`, alongside the tracer's in-process assertions which stay
exactly as they are:

- driven in-process against a `LoopbackLink`, the ground consumer's own loop turns framed
  batches into decoded signal records carrying the message name, each signal's name, its
  value, and its unit taken from the DBC
- the decoded values equal the values that were encoded into the frame on the car side,
  compared against the DBC-encoded source values rather than against opaque bytes
- a frame whose message the DBC does not describe is counted as an undecodable record and
  logged once with its id, and does not stop the loop
- corrupt batches fed into the same loop increment the deframer's counters and produce no
  decoded output at all
- the consumer's periodic link-health line reports batches received, batches discarded by
  each failure class, records decoded, and records that failed to decode
- the loop exits on the stop event within a bounded time even when the link is silent, so a
  terminated session does not hang the process
  </behavior>
  <action>
Create `src/telemetry/ground/cli.py` as the headless ground-station entry point, runnable as a
module. A plain single-threaded loop, no asyncio — `01-CONTEXT.md` locks that for Phase 1, and
asyncio's value only appears in Phase 2 when the process starts serving several browser
clients at once.

Read the same `config/logger.json` the car reads, with the same `--config` default and the
same per-field CLI overrides. Both ends read one file because the dictionary, the allowlist,
and the encoder options must match on both sides — a mismatch there is a caller error, not
something negotiated over the wire, and negotiating it is explicitly Phase 4's job.

Build the ID dictionary and the DBC database from the configured DBC path, construct the
configured link, construct the `Deframer`, and loop: receive, feed, and for every recovered
frame decode its payload against the DBC and emit one record per decoded signal.

Emit decoded records to stdout as newline-delimited JSON — one object per signal with the
channel or topic, the message id, the message name, the signal name, the value, the unit, and
the frame timestamp. This is a deliberate continuation of the existing project convention
that stdout carries machine-readable output and stderr carries human output; it also means
Phase 2 can consume this stream while the dashboard is being built rather than waiting for it.
Support an optional flag to also append the same records to a file.

Emit a link-health line to stderr on a fixed interval: batches received, batches discarded by
each failure class, records decoded, records that failed to decode, and the elapsed time.
These are the counters Phase 6's link-health indicator will read, so name the fields as they
will be consumed rather than for this CLI's own convenience.

Handle a DBC decode failure the way every other layer in this phase handles bad input: catch
by type, count it, log the first occurrence per message id with the id attached, and continue.
`src/new_logger.py` swallows exactly this case with a bare pass at lines 244 to 247, which is
one of the specific behaviours CAP-06 exists to eliminate — do not reproduce it here just
because this file is on the ground rather than on the car.

Install interrupt and terminate handlers that set a stop event, and give `recv` a bounded
timeout so a silent link cannot leave the process unkillable.

Added to `tests/test_end_to_end.py` — phase success criterion 4, asserted at the process level:

- start the ground CLI as a subprocess bound to an ephemeral loopback UDP port, and wait until
  it reports the port it is actually listening on rather than assuming one
- start the car-side logger CLI as a second subprocess with the synthetic frame source, a
  bounded duration, a temporary archive root, and the link kind and remote port overridden to
  point at the ground process
- assert the ground process's stdout carries decoded signal records naming messages from the
  configured allowlist, with values that decode against the DBC
- assert at least one message from each of the two configured channels appears, so the
  two-bus path is exercised end to end and not only the first channel's
- assert the car process exits zero, left a complete session directory with a `.done` marker,
  and reported zero archive-path drops in its JSON summary — the archive path is unaffected by
  anything happening on the live path
- assert the ground process's final link-health output reports zero batches discarded on a
  clean loopback run
- do not assert that every transmitted frame arrived. UDP's unacknowledged loss is a modelled
  feature of the real radio link, and asserting delivery would make this test flaky for a
  reason that is not a defect. Assert that what arrived was correct and that a nonzero,
  substantial fraction arrived
- give both subprocesses hard timeouts and terminate them in a `finally` block, so a hang
  fails the test rather than hanging the suite
- the test docstring states plainly that no radio hardware, no vehicle hardware, and no second
  machine is involved: two processes, one loopback interface
  </behavior>
  <action>
Write the two-process test. Reuse the subprocess-launch shape from
`tests/test_measure_cli_smoke.py` rather than inventing a new one.

Discover the ground process's bound port by reading its startup line rather than hardcoding a
port number or binding one in the test and hoping it stays free — the UDP link exposes its
actual bound address for exactly this reason, and a hardcoded port makes the suite fail on any
machine where that port happens to be in use.

Order the startup so the ground process is listening before the car process begins sending,
and give the car process a bounded duration so the test terminates on its own rather than
depending on a kill.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Denial of Service | Ground CLI receive-and-decode loop | high | mitigate | Every layer catches by named type and counts: framing failures in the deframer, CFR failures in the decoder, DBC failures in this CLI. No input can raise an unhandled exception out of the loop. The loop is asserted to survive corrupt batches and to keep decoding afterward. |
| T-01-28 | Denial of Service | DBC decode of an attacker-chosen or malformed payload | high | mitigate | Decode failures are caught by type, counted, logged once per message id, and skipped. The legacy bare-pass swallow is explicitly not reproduced — a counted failure is both safe and visible, where a swallowed one is only safe. |
| T-01-29 | Denial of Service | A silent or hostile link leaving the process unkillable | medium | mitigate | `recv` carries a bounded timeout and the loop checks the stop event every iteration, so the process exits promptly whether the link is silent, saturated, or hostile. |
| T-01-08 | Spoofing | A forged batch injected at the bound UDP port | low | accept | Phase 1 runs on loopback and a trusted pit LAN, with nothing actuated downstream of decoded values and no dashboard yet. The CRC is an error-detection code and is explicitly not an authentication mechanism — that framing must stay documented and must not be silently reinterpreted as security later. Re-assess at Phase 9. |
