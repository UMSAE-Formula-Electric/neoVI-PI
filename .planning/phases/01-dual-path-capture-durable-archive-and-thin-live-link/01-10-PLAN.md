  <name>Task 1: The telemetry pipeline thread — drain, batch, encode, frame, send</name>
  <files>src/telemetry/logger/pipeline.py, tests/test_logger_cli_smoke.py</files>
  <read_first>src/telemetry/capture/fanout.py, src/telemetry/wire/batcher.py, src/telemetry/wire/encoder.py, src/telemetry/framing/cobs_frame.py, src/telemetry/link/base.py</read_first>
  <behavior>
Written in `tests/test_logger_cli_smoke.py`, replacing 01-02's placeholder skip, driving the
pipeline directly against a `LoopbackLink` and a `Deframer` so every assertion is about frames
that actually came back out the other end.

Batch closing:
- a batch closes at the configured frame count, and the receiving deframer recovers exactly
  that many records from it
- a batch closes on age when fewer than the configured count have arrived, so a quiet bus
  still delivers within the configured latency rather than waiting for a full batch
- a batch closes early when the next frame's timestamp would fall outside the CFR delta-t
  window, and the frame that triggered the close opens the next batch rather than being
  dropped. Construct this case explicitly with two frames separated by more than the window,
  and assert both frames arrive on the far side across two batches
- batch sequence numbers advance and wrap, and the receiving side sees them in order over a
  loopback link

Counters and error handling:
- frames the encoder rejects — an id absent from the dictionary, an over-length payload — are
  counted by their own named error type, logged with frame context, and skipped without
  taking the batch or the thread down
- the pipeline reports frames sent, batches sent, bytes sent, and per-error-type counts
- a link whose `send` raises is counted and logged, and the pipeline continues: the live path
  is explicitly lossy and a transmit failure must never propagate into the capture or archive
  path
- on the stop event the pipeline flushes the batch in progress before exiting, so a shutdown
  does not silently discard frames already drained from the deque
  </behavior>
  <action>
Create `src/telemetry/logger/pipeline.py` holding `TelemetryPipeline`, the consumer end of the
fan-out's telemetry deque, running in its own thread.

Its loop pops from the left of the deque — the deque evicts from the left when full, so
consuming from the same end preserves ordering — encodes each frame with the shared `Encoder`,
and accumulates records into a batch. Close and send the batch on whichever comes first:
the configured frame count, the configured maximum batch age, or a frame whose timestamp would
fall outside the CFR delta-t window relative to the current batch's base timestamp. The third
condition is a correctness requirement, not a tuning knob: `wire/encoder.py` raises
`BatchWindowExceeded` for exactly that case, and the pipeline must close the batch and start a
new one rather than letting the exception surface as a lost frame.

Sending is: pack the batch, frame it with CRC and COBS, then one `Link.send` call. Nothing
else. The link is whatever the config selected, and the pipeline neither knows nor cares which
implementation it holds.

Catch and count by specific type. `CfrError` and its subclasses cover encoder rejections;
`FramingError` covers batch and framing failures; a link exception covers transmit failures.
Each gets its own counter field and a log record carrying the frame's channel, id, and
timestamp. None of them may terminate the thread, because the live path is lossy by design and
the archive path must not be affected by anything that happens here.

Follow the same thread discipline as the archive runner: name the thread, poll the shared
stop event every iteration, and flush the batch in progress before returning. Unlike the
archive runner this thread may be a daemon — it has no durability obligation, and that
asymmetry is the point of the whole fan-out.
  </action>

    <automated>python -m pytest tests/test_logger_cli_smoke.py -x -q --tb=short</automated>
  </verify>
  <done>
Batches close on count, on age, and on the CFR window boundary, and every frame arrives on the

  <action>
Create `src/telemetry/logger/cli.py` as the car-side entry point, runnable as a module.

Argument handling per `01-CONTEXT.md`'s locked decision: `--config` names the file and
defaults to `config/logger.json`; individual CLI flags override individual config fields, and
everything not overridden comes from the file. Provide at minimum overrides for the archive
root, the link kind, the frame source, and a bounded run duration. Configure the logging
handlers here — this is an entry point, and no library module under `telemetry` may configure
logging itself.

Offer two frame sources: the hardware source, and the synthetic source built on
`telemetry.synth.generator.SyntheticFrameSource` so the whole process is runnable and testable
with no device attached. The synthetic path is not a test fixture bolted on — it is how anyone
demonstrates the logger on a laptop, and how the soak test in 01-13 drives real code.

Wire the process in this order: load and validate config, resolve the allowlist against the
DBC, create the session, open the archive writer, construct the configured link, build the
fan-out, start the archive runner and the telemetry pipeline, install signal handlers for
interrupt and terminate that set the stop event, then run the capture loop. Install the signal
handlers before starting any thread, following `src/new_logger.py`'s ordering at lines 329 to
332 — a signal arriving during startup must not leave a half-built process with an open
archive.

Shut down in strict order: stop capture, push the sentinel, join the archive runner so it
drains and the writer flushes, close the writer, then call `mark_done`. The marker is written
only if the archive closed cleanly — an interrupted or failed session must be distinguishable
afterward, and that distinction is the whole of ARCH-05.

Emit two outputs at shutdown. A human-readable report to stderr naming frames captured, frames
archived, frames sent, both queue high-water marks, telemetry discards, allowlist-filtered
count, and every error counter. A machine-readable JSON summary of the same values to stdout,
so a test and a future health check read the same numbers a person does. Keep stdout for
machine-readable output only, matching the convention already in the codebase.

Do not carry over `src/new_logger.py`'s hardcoded transmit configuration or its commented-out
alternative code paths. Nothing in Phase 1 transmits on the CAN bus, and dead commented code
is explicitly flagged as a practice not to continue.
