<objective>
Make a crashed archive readable and an interrupted session identifiable — ARCH-02's
substance — and write the physical power-pull procedure ARCH-03 asks for by name.

Purpose: `01-RESEARCH.md` Pattern 2 is this phase's single highest-risk finding, verified by
writing, crashing, and reading real files rather than by reading documentation. Both of
`mcap` 1.4.0's obvious read paths fail on a crashed file, and one of them fails silently: on
a file holding fifty complete, uncorrupted records, `NonSeekingReader(f).iter_messages()`
with its default `log_time_order=True` recovered zero of fifty, because sorting forces the
whole stream to be drained into memory before anything is yielded and the missing footer
raises during that drain. `mcap.reader.make_reader()` is worse — it raises a nonsense
`RecordLengthLimitExceeded` with an absurd record length rather than signalling "no footer."
The only configuration that works is `NonSeekingReader(f).iter_messages(log_time_order=False)`
wrapped to catch both `EndOfFile` and a bare `struct.error`.

Output: one named recovery function so that call is written once and never re-derived
inline, tests that pin the finding so a later reader cannot quietly simplify it back to the
default, and a bench procedure for the proof no automated test can supply.
</objective>

reader configuration with the obvious one: against the same footer-less fifty-record file,
assert that going through `mcap.reader.make_reader` raises rather than returning records, and
that `NonSeekingReader(...).iter_messages()` called with its own default ordering yields
nothing. The test's docstring states that these two assertions exist to document why
`recover_session` uses the configuration it uses.

One kill-based proxy test, driven by `tests/crash_writer_child.py`:
- the parent spawns the child with an output path, a record count large enough to outlive
  several flush cadences, and the flush cadence from config
- the child writes frames through the real `ArchiveWriter` and prints one line to stdout each
  time an fsync completes, naming the cumulative record count at that point
- the parent reads those lines until it has seen at least two fsync confirmations, then kills
  the child process outright
- the parent asserts: `recover_session` returns at least as many records as the last
  confirmed fsync reported; every recovered record unpacks; the session directory has no
  `.done` marker; `is_session_complete` returns false

Session completeness: `is_session_complete` returns true for a directory with the marker and
false for one without.

  <action>
Create `src/telemetry/archive/reader.py` with exactly one supported recovery entry point and
a module docstring that states, in the first paragraph, why the obvious calls are wrong and
must not be substituted — a later contributor simplifying this back to `make_reader()` is the
specific failure this file exists to prevent.

`recover_session(mcap_path)` opens the file in binary mode, constructs
`mcap.reader.NonSeekingReader`, iterates `iter_messages(log_time_order=False)` in a `for`
loop, and wraps that loop in a `try` catching `(mcap.exceptions.EndOfFile, struct.error)`.
Both exception types are needed: a clean end between records raises the first, a truncation
inside a record header raises the second, and `struct.error` is not an `mcap` exception type
so it cannot be caught by an `mcap`-only handler. Everything accumulated before the exception
is already recovered and is returned. Return a small frozen result carrying the recovered
`(channel_topic, RawFrame)` pairs, the record count, and whether the read ended early.

Unpack each message payload through `archive/record.py`'s `unpack_frame`, using the message's
`log_time` for the frame timestamp — the layout is defined once in that module and this
reader must not re-derive it.

Add `is_session_complete(session_dir, done_marker_filename)` returning whether the marker
file is present. This is the predicate Phase 8's SYNC-02 will need to avoid copying a session
mid-write, and it belongs beside the recovery path rather than being re-implemented later.

Create `tests/crash_writer_child.py` as a standalone script invoked as a subprocess by the
test. Give it an `argparse` interface taking the output directory, the number of records, and
the flush cadence. It builds a real session through `new_session`, writes synthetic frames
through the real `ArchiveWriter`, and prints a confirmation line to stdout with an immediate
flush every time a flush-and-fsync completes. It must never call `mark_done` — the point is
that a killed session has no marker.

Give `tests/test_archive_crash_recovery.py` a module-level docstring stating its own scope
limit plainly, and repeat that limit as an inline comment directly above the kill in the
proxy test. The limit: killing a process does not crash the operating system, so any bytes
already handed to `write()` survive in the OS page cache and are readable afterward even if
they were never synced to the device. An implementation that never calls fsync at all can
therefore pass this test. What this test proves is write-cadence correctness. Proving fsync
correctness needs either a page-cache drop between the kill and the read — which requires
root and is unavailable on this Windows dev box — or the physical power-pull procedure in
`docs/power-pull-test.md`, which is the real ARCH-03 proof and cannot be waived.
  </action>

tracer deferred. The CM4 has no RTC battery, so the wall clock can be epoch-garbage at boot
