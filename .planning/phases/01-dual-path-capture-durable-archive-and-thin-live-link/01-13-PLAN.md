Prove CAP-02 the way phase success criterion 3 states it: a sustained run at full combined bus
load reporting zero archive-path drops, with high-water marks, discard counts, and error counts
surfaced as numbers rather than as the absence of a failure.

criterion asks for the counters explicitly, and `01-RESEARCH.md`'s Open Question 2 asks for
per-stage timing on top — because the question nobody has answered yet is which stage is
closest to its limit once the encoder and the archive writer run concurrently under real thread
scheduling, and an aggregate drop count of zero does not answer it.

Output: a repeatable load test whose reported numbers go into the phase's verification record.

with the `slow` marker 01-02 registered so it stays out of the quick loop and runs on the full
suite.

Drive `telemetry.synth.generator.SyntheticFrameSource` through the real `FanOut`, the real
`ArchiveRunner` and `ArchiveWriter`, and the real `TelemetryPipeline` over a `LoopbackLink`.
Not the measurement CLI — `01-VALIDATION.md` is explicit that the load must go through the
production fan-out and writer, because a test that exercises a different path proves nothing
about the one that runs on the car.

Make the simulated bus duration an environment-variable override with a bounded default that
keeps the test to a reasonable wall-clock time on a laptop, and record both the configured
duration and the resulting frame count in the output. Use the two configured channels so the
load is genuinely combined across both buses, and split the synthetic stream between them so
the per-channel counts are meaningful.

Assert, in this order:
- the archive-overflow flag is false and the archive-path drop count is exactly zero
- reading the closed archive back through `recover_session` yields exactly the number of
  frames submitted to the archive queue, with no duplicates — assert on the multiset of
  frames, not only on the count, so a reordering or a duplicated write is caught
- the telemetry path's discard count plus its enqueued count plus its allowlist-filtered count
  equals the total frames submitted, so every frame is accounted for on both sides
- every error counter on the fan-out, the runner, and the pipeline is zero for a clean run
- the achieved sustained frames-per-second, computed from wall clock, meets the combined
  target rate

For that last assertion, put the dev-hardware caveat in the failure message itself rather than
only in a comment: this suite runs on x86-64 while the target is the CM4's Cortex-A72, no
figure in `01-RESEARCH.md` was measured on that core, and `01-VALIDATION.md` lists running this
same test on the CM4 as a manual-only verification that this run does not replace. A failure
here on the dev box means the code is too slow to be worth carrying to hardware; a pass here
does not mean it is fast enough on hardware.

  <action>
Add per-stage timing to the soak and emit a single structured record of the whole run.

Measure, at minimum: total wall clock and achieved frames per second; the fan-out's per-submit
time distribution; the archive writer's records-per-second and its flush count and total time
spent in flush and sync; the telemetry pipeline's batches per second, bytes per second, and
time spent in encode versus in framing versus in `Link.send`. Report a median and a high
percentile for the per-stage figures rather than a mean alone — a mean hides exactly the
stalls this measurement exists to find.

Emit the whole record as JSON to the test's captured output and also write it to a file under
the test's temporary directory, then assert the file parses and carries every field. The
executor copies the reported numbers into the plan SUMMARY, which is what phase verification
reads for success criterion 3.

Include in the same record: both queues' high-water marks, the telemetry discard count, the
allowlist-filtered count, every error counter, the configured queue depths and flush cadence
the run used, and the machine's platform and Python version — a timing number without the
machine it was measured on is not a fact anyone can use later.

State in the record, as a field rather than only in a docstring, that these figures were
measured on this machine and not on the CM4. Phase 0 was bitten three separate times by prose
figures that disagreed with measured reality, including once by a plan carrying an inherited
wrong number; a timing artifact that does not carry its own provenance is the same trap set
again.
