<objective>
Close the two gaps between "the process started" and "the operator can trust what they see": the
power-sequencing race at boot, and what the status file says when a session ends badly.

The CM4 will frequently finish booting before the CAN bus is powered. Exiting on that would turn a
completely normal race into a failure needing a restart, and `Restart=always` would turn it into a
crash-loop that burns through the unit's restart budget for no reason. So the logger stays alive,
retries with backoff, and says `waiting-for-hardware` — a state deliberately distinct from an error.

**Marks:** none. Addresses OPS-01 and OPS-02. OPS-02 is marked by 03-05; OPS-01's status is decided
by 03-07. Do not touch `.planning/REQUIREMENTS.md` in this plan.

Output: `src/telemetry/ops/hardware_wait.py`, its call site ahead of session creation, and the
terminal-state write on the way out.
</objective>

  <name>Task 1: `telemetry.ops.hardware_wait` — retry with backoff, catching the SDK's own exception type</name>
  <files>src/telemetry/ops/hardware_wait.py, tests/test_ops_hardware_wait.py</files>
  <read_first>
    - `src/telemetry/capture/hardware_source.py` — the whole file. This is the strongest analog in the phase: `_default_sdk()`'s lazy import, the `except self._sdk.RuntimeError` catch shape and the comment explaining it, `open()`'s `find_devices()` → empty check → serial match sequence, and the `self._stop_event.wait(timeout=...)` poll idiom.
    - `tests/test_hardware_source.py` — the existing fake-SDK construction this plan's tests reuse rather than reinvent.
  </read_first>
  <behavior>
    - A fake SDK whose `find_devices()` returns a non-empty tuple on the first call makes `wait_for_hardware` return True immediately, with `on_waiting` never called.
    - A fake SDK returning an empty tuple twice and then a non-empty tuple returns True after exactly three `find_devices()` calls, with `on_waiting` called twice.
    - A fake SDK whose `find_devices()` raises that fake SDK's OWN `RuntimeError` attribute — a class that deliberately does NOT subclass the builtin — is treated as "not present yet" and retried, not propagated. This is the regression that matters: `ics.RuntimeError`'s MRO does not include the builtin, verified live twice on this project.
    - An exception type the SDK does not own propagates out of `wait_for_hardware` rather than being swallowed.
    - Setting `stop_event` while the loop is waiting makes `wait_for_hardware` return False promptly — assert the total injected wait time consumed is bounded, using an injected sleep/wait seam rather than a real sleep.
    - Backoff grows from `initial_backoff_s` and never exceeds `max_backoff_s`, asserted against the recorded sequence of requested timeouts.
    - `on_waiting` receives the attempt number and the backoff about to be waited.
    - Importing `telemetry.ops.hardware_wait` performs no SDK import; constructing the call with an injected fake never touches the real `ics` module.
  </behavior>
  <action>
Create `src/telemetry/ops/hardware_wait.py` with a single public function:

`wait_for_hardware(*, stop_event, on_waiting=None, sdk=None, initial_backoff_s=0.5,
max_backoff_s=5.0) -> bool` — returns True once devices are found, False if `stop_event` fires first.

    - `_default_sdk()` lazily imports and returns the real `ics` module, copied in shape from
      `hardware_source.py` including its docstring's reasoning: importing this module must never
      touch the SDK, and constructing with an injected fake must never either. That is what keeps
      this unit-testable on the Windows dev box, where no native driver exists at all.
    - Loop while `stop_event` is unset: call `sdk.find_devices()`; catch `sdk.RuntimeError` — via the
      injected SDK object's own attribute, NEVER the builtin name — and treat it as an empty result.
      Copy `hardware_source.py`'s explanatory comment about why, rather than paraphrasing it away:
      this is the single most-repeated previously-hit failure mode in this project.
    - Treat BOTH outcomes as "not present yet": a caught SDK error and an empty devices tuple.
      03-RESEARCH.md verified the first live (driver entirely absent raises), and flags the second as
      inferred from `HardwareFrameSource.open()`'s already-merged code rather than re-verified on
      Linux with the driver present and zero devices attached. Handling both identically is what
      makes that open question harmless. Say so in the docstring, and name it as the thing to confirm
      at first real Pi bring-up.
    - Call `on_waiting(attempt, backoff_s)` before each wait, then
      `stop_event.wait(timeout=backoff_s)` — never a bare `time.sleep`, so a stop signal interrupts
      immediately instead of waiting out a full backoff. Grow the backoff (double it) and clamp at
      `max_backoff_s`.
    - There is no timeout parameter and no maximum attempt count. On the car, waiting indefinitely
      is the correct behaviour; `stop_event` is the only exit (D: the logger stays alive and retries).
    - `logger = logging.getLogger(__name__)` at module scope. Log the first wait at WARNING naming
      the state, then subsequent waits at DEBUG — a bus that stays unpowered for minutes must not
      fill the journal.

Write the behaviour assertions first against a hand-rolled fake SDK modelled on the one already in
`tests/test_hardware_source.py`, including a fake `RuntimeError` attribute that subclasses
`Exception` directly so the builtin-shadowing regression is genuinely exercised.
  </action>

  <behavior>
    - With `--source hardware` and a fake SDK reporting no devices, `main()` does not create any session directory under the archive root while waiting, and the status file's state reads `waiting-for-hardware`.
    - Once the fake SDK starts reporting a device, the same run proceeds to create a session and the status file's state becomes `capturing`.
    - Setting the stop event while waiting exits with code 0 and removes the status file — an operator stopping a logger that never saw hardware is a clean stop, not an error.
    - With `--source synthetic`, `wait_for_hardware` is not called at all.
    - A run whose archive does not close cleanly leaves a status file with state `stopped-error` whose detail names the failing condition, and the file is NOT removed.
    - A run whose capture loop raises leaves state `stopped-error` even if the writer itself closed without error.
    - A run that finishes cleanly leaves no status file.
    - A DBC-load or allowlist-resolution failure publishes `stopped-error` before `SystemExit(1)`; a config-load failure publishes nothing, because the heartbeat path is only known after the config parses.
  </behavior>
  <action>
Two edits in `src/telemetry/logger/cli.py`, both additive to what 03-01 and 03-02 already wired.

**The boot race.** In `main()`, after the disk gate and before `_run_session`, when
`args.source == "hardware"`, call `wait_for_hardware(stop_event=stop_event, on_waiting=...)` with an
`on_waiting` callback that `publish_now`s a `waiting-for-hardware` snapshot whose `detail` names the
attempt number and the backoff. It must sit here, before `_run_session`, because `_run_session`
calls `new_session()` first and `HardwareFrameSource.captured_frames()` lazily calls `open()`, which
fails fast by design — waiting inside `_run_session` would leave an empty session directory behind
on every unpowered boot. If `wait_for_hardware` returns False (the stop event fired), remove the
status file and return without a session: this is a clean stop.

Accept an injectable seam for the wait (an optional keyword parameter defaulting to the real
`wait_for_hardware`, matching the disk-check seam 03-02 added) so the tests drive the hardware race
without an SDK. Do not add a test-only branch inside the production function.

Note in a comment that a device disappearing between the successful wait and `open()` is still
possible; that narrow race is already handled by `_run_session`'s existing broad `except Exception`
around the capture loop, which now results in a `stopped-error` terminal state via the second edit —
not by adding a second retry layer.

**The terminal state.** In `_run_session`, set a local flag in the existing
`except Exception:` branch that already logs "capture terminated by an unhandled exception". After
the existing shutdown block and after `_log_human_summary` — never interleaved with the strict
archive lifecycle ordering the module docstring fixes — decide the terminal state:
    - if the capture flag is set, or `archive_closed_cleanly` is False, or
      `fan_out.counters.archive_write_failure` or `archive_overflow` is set:
      `publish_now` a `stopped-error` snapshot whose `detail` names which of those conditions fired,
      with the same counters in `extras`, and leave the file in place. A human arriving later must
      find the reason, not an absence.
    - otherwise stop the publisher and `remove()` the file (03-01's clean path).
Stop the publisher thread in both branches before the final synchronous write, so the periodic
`capturing` tick can never race ahead of the terminal write.

Also wrap the existing DBC-load and allowlist-resolution failure branches in `main()` so each
publishes a `stopped-error` snapshot naming the failure before its `raise SystemExit(1)`. Leave the
config-load branch alone: at that point the heartbeat path is not yet known, so no status file can
exist. That asymmetry is real and the runbook (03-07) must document it — a service that is running
with no status file at all means the config failed to parse, and the journal is where the reason is.

Extend `tests/test_logger_cli_ops.py` with the behaviours above, driving `--source hardware` through
the injected wait seam and a fake SDK, and forcing an unclean archive close through the existing
counters rather than by corrupting a file.
  </action>
