  <name>Task 1: Package gate — the real LED driver's two dependencies</name>
  <what-built>
Nothing yet in this plan. This checkpoint runs FIRST because it decides the scope of Task 2.

03-RESEARCH.md established, from Intrepid's own public documentation repository rather than from
web search or recall:

- The neoVI PI specification page lists **10 programmable tri-color LEDs**, separate from the
  CAN/CAN FD channel status LEDs (which show no evidence of being software-addressable).
- Intrepid's `neoVI_PI-docs` repository has a page "Controlling Membrane LEDs and Trigger Button"
  and ships a working reference script at `static/downloads/membrane.py`. Its first lines were
  fetched verbatim: it imports `smbus` and `RPi.GPIO`, and targets an LED driver at I2C bus `10`,
  address `0x3c`.
- Setup also requires enabling an `i2c_vc` device-tree overlay in the boot config. Whether that
  file is at `/boot/config.txt` (as Intrepid's doc says) or `/boot/firmware/config.txt` (where
  current Raspberry Pi OS Bookworm images put it) was NOT confirmed against a real neoVI PI image
  and is flagged as an assumption.

**What this means:** a concrete `MembraneLedIndicator` needs two PyPI packages — `smbus` (or its
maintained fork `smbus2`) and `RPi.GPIO`. Neither is installed. Neither has been run through this
project's package-legitimacy-check seam. This project's precedent (the 01-01 blocking checkpoint)
is that adding a package is a human decision, not a default action.

**What this plan does unless you say otherwise:** ship `LedIndicator` (a `typing.Protocol`) and
`NullLedIndicator` (a no-op), wire the call site into the heartbeat publisher, add nothing to
`requirements.txt`, and write no I2C or GPIO code.
  </what-built>
  <how-to-verify>
If you want to confirm the packages before deciding, check them yourself:
- `https://pypi.org/project/smbus2/`
- `https://pypi.org/project/RPi.GPIO/`
and Intrepid's source for the claims above:
- `https://github.com/intrepidcs/neoVI_PI-docs` → `docs/control-membrane-leds-and-trigger-button.md`
  and `static/downloads/membrane.py`

Decide whether the physical LED matters for this testing season. Points worth weighing: the status
file plus `telemetry-status` already answers "is it alive and capturing" for anyone with a laptop or
an SSH session, and a physical LED is what answers it for someone standing at the car with neither.
Against that: the service is meant to run as a dedicated non-root user, and I2C/GPIO access needs
explicit group membership, which is additional deployment surface on a machine nobody logs into.
  </how-to-verify>
  <resume-signal>
Reply with one of:
- `defer` — ship `NullLedIndicator` only, no packages, no I2C code. This is the planned default and
  the phase continues unchanged.
- `approve-and-replan` — you want the real membrane LED this milestone. Nothing is installed on this
  reply; the packages go through the legitimacy-check seam and a new plan is written for the
  concrete driver, because it also needs real hardware to verify and this phase has exactly one
  hardware-only item budgeted.
  </resume-signal>

  <files>src/telemetry/ops/led.py, src/telemetry/ops/heartbeat.py, tests/test_ops_led.py, tests/test_ops_heartbeat.py</files>
  <read_first>
    - `src/telemetry/link/base.py` — the whole file. `LedIndicator` mirrors this structurally: a `typing.Protocol`, a minimal method surface, and a docstring naming which concrete implementations exist and which phase adds each one.
    - `src/telemetry/ops/heartbeat.py` `HeartbeatPublisher.__init__` and its write loop (from 03-01)
  </read_first>
  <behavior>
    - `NullLedIndicator` satisfies `LedIndicator` — assert via a `typing.runtime_checkable` isinstance check or by binding it to an `LedIndicator`-annotated name that a type check would accept, and by calling both methods.
    - `NullLedIndicator.set_state(...)` accepts every name in `HEARTBEAT_STATES` and returns `None` for each.
    - `NullLedIndicator.set_state(...)` and `.close()` are safe to call repeatedly and after `close()`.
    - A `HeartbeatPublisher` constructed with no `led` argument still drives an indicator: injecting a recording double instead and running N ticks yields exactly N `set_state` calls, whose arguments equal the states the publisher wrote.
    - An indicator whose `set_state` raises does not prevent the status file from being written and does not kill the publisher thread — the file is the primary indicator and a broken LED must never take it down.
    - `HeartbeatPublisher.join()`/stop calls `close()` on the indicator exactly once.
  </behavior>
  <action>
Create `src/telemetry/ops/led.py`.

    - `LedIndicator(Protocol)` with exactly two methods: `set_state(self, state: str) -> None` and
      `close(self) -> None`. Two methods, not more — the project's Protocol convention
      (`Link` has three, `FrameSource` has a comparable surface) is a minimal surface, and every
      method added here is a method a future concrete driver must implement.
    - `NullLedIndicator` — the implementation this phase ships. Its docstring names the confirmed
      hardware a concrete implementation would target (an I2C-attached LED driver on the neoVI PI's
      membrane panel, bus 10, address 0x3c, per Intrepid's own reference script), names the two
      packages such an implementation needs, and states that neither is installed and that adding
      them is gated by the human checkpoint in this plan. Do not restate the LED count or the driver
      part number as fact beyond what 03-RESEARCH.md cites — the part number was read from a comment
      in the vendor script and its exact identity was not independently confirmed.
    - Do NOT add a `/sys/class/leds` code path. No evidence was found that generic Pi LED entries
      are wired on this carrier board, and Intrepid built a bespoke I2C panel instead, so a
      speculative second path would be an unverified claim in code.

Then wire the call site in `src/telemetry/ops/heartbeat.py`:

    - `HeartbeatPublisher.__init__` gains `led: Optional[LedIndicator] = None`, defaulting to
      `NullLedIndicator()` when not supplied. Defaulting inside the constructor rather than at the
      `logger/cli.py` call site is deliberate: it keeps this plan out of `logger/cli.py` entirely,
      which is what lets it run in the same wave as 03-02.
    - Every write — the periodic tick and `publish_now` — calls `led.set_state(snapshot.state)`
      AFTER the status file has been replaced, wrapped so any exception from the indicator is logged
      once at WARNING and swallowed. The status file is the primary indicator (D); a failing
      physical indicator must never take it down. Use the same log-once-then-suppress discipline the
      SSE hub already uses for repeated write failures rather than logging at 1 Hz.
    - Stopping the publisher calls `led.close()` exactly once.

Write the behaviour assertions first, using a recording double that captures every `set_state`
argument and a raising double for the failure case.
  </action>
