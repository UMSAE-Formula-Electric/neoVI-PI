**Layer 2 — ops package (`src/telemetry/ops/__init__.py`, `src/telemetry/ops/heartbeat.py`).**
    - `HEARTBEAT_STATES`: a tuple of exactly the five states D locks — `booting`,
      `waiting-for-hardware`, `capturing`, `degraded`, `stopped-error`. Five, not six: a clean stop
      is signalled by the file's ABSENCE, not by a sixth state. Expose module constants for each.
    - `HeartbeatSnapshot` frozen dataclass: `state: str`, `detail: Optional[str]`,
      `extras: Mapping[str, object]`. This is the seam later plans fill (03-02 disk state, 03-03
      hardware wait and terminal states) — the publisher itself must stay ignorant of disk and
      hardware.
    - `write_heartbeat(path, payload, *, now_fn=time.monotonic, wall_clock_fn=time.time)`: build the
      JSON payload, write it to a temp file created in `path.parent` (never a fixed temp dir —
      `os.replace` is only atomic within one filesystem, and a tmpfs `/tmp` on the real image would
      make it a cross-device rename), flush, `os.fsync`, then `os.replace(tmp, path)`. Name the temp
      file with the writing process's pid so two writers could never collide. `mkdir(parents=True,
      exist_ok=True)` on `path.parent` first. In the docstring, scope the atomicity claim to Linux
      (the deployment target) — on the Windows dev box `os.replace` still succeeds over an existing
      file, which is what makes this testable here, but the POSIX rename guarantee is what the car
      relies on.
    - Payload fields: `schema_version` (1), `state`, `detail`, `written_at_monotonic`,
      `written_at_utc` (ISO-8601, informational only — the CM4 has no RTC battery so this can be
      epoch-garbage at boot and MUST NOT be used for the staleness comparison), `pid`, and `extras`
      merged under an `extras` key. Serialize with `json.dumps(..., sort_keys=True)`.
    - `read_heartbeat(path, *, stale_after_s, now_fn=time.monotonic) -> HeartbeatReading` where
      `HeartbeatReading` carries `payload`, `age_s`, `stale: bool`, `staleness_reason:
      Optional[str]`. Staleness rules, all three:
        `now < written_at_monotonic` → stale, reason `clock-went-backwards`. This is the
        reboot-boundary case verified in 03-RESEARCH.md Pitfall 5: `time.monotonic()` IS comparable
        across processes on one boot (Python 3.5+), but its reference point resets at reboot, so a
        surviving file can produce a negative age that a naive `age > threshold` test reads as
        fresh — the worst possible outcome for a health indicator.
        `age_s > _IMPLAUSIBLE_AGE_S` (a named module constant, 86400.0 — a chosen heuristic, not a
        measurement; say so in the comment) → stale, reason `implausible-age`.
        `age_s > stale_after_s` → stale, reason `stale`.
      Raise a named `HeartbeatReadError` for a missing file, unreadable file, non-JSON content, or a
      payload missing `state`/`written_at_monotonic` — the reader never guesses.
    - `HeartbeatPublisher(path, interval_s, stop_event, snapshot_fn, *, now_fn=time.monotonic)`:
      `start()` spawns a daemon thread named `ops-heartbeat` (the project's established
      thread-naming convention) that loops on `stop_event.wait(timeout=interval_s)` writing
      `snapshot_fn()`; `publish_now(snapshot)` writes one synchronously (used for `booting` before
      the thread exists); `join(timeout)`; `remove()` deletes the file, tolerating absence.
      In the class docstring, state explicitly that `snapshot_fn` reads Phase 1's counter
      dataclasses concurrently with their single writer thread: each individual int field read is
      atomic in CPython so no torn value is possible, but the SET of counters can be momentarily
      inconsistent. That is acceptable for a liveness indicator and does NOT change those counters'
      documented "safe to read only after the writer stops" contract for the shutdown summary.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| logger process → local filesystem (status file) | The only cross-process channel this phase creates; a second process reads what the logger writes |
| `config/logger.json` on disk → logger process | Untrusted-shaped input crosses into typed runtime settings |
| physical access to the car → the Pi's filesystem | Anyone who can reach the car can read or edit the status file |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | `ops/heartbeat.py` write path | medium | mitigate | Temp-write in the target's own directory + `fsync` + `os.replace`; a reader never observes a torn file. Pinned by the concurrent-read assertion in Task 2. |
| T-03-02 | Spoofing | `ops/heartbeat.py` staleness check | medium | mitigate | `now < written_at_monotonic` and implausible-age both report STALE, so a file surviving a reboot can never read as fresh (03-RESEARCH.md Pitfall 5). Pinned by two Task 2 assertions. |
| T-03-03 | Information Disclosure | status file payload (session name, paths, counters) | low | accept | No network exposure this phase — remote readout is Phase 6. Physical access to the car already implies filesystem access; the archive itself is a far richer target sitting on the same disk. |
| T-03-04 | Tampering (input validation, ASVS V5) | `_parse_ops` in `logger/config.py` | medium | mitigate | Fail-closed typed loader raising `LoggerConfigError` naming key and value, plus two cross-field checks; no silent default can produce an un-written heartbeat or an inverted threshold pair. |
| T-03-05 | Denial of Service | 1 Hz `fsync`ed writes to one path | low | accept | One fixed-size file replaced in place at 1 Hz, against an archive already flushing on a 0.25 s / 1000-record cadence — negligible additional I/O. Revisit only if a measured session shows otherwise. |
| T-03-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan installs nothing; `requirements.txt` is unchanged. Any package addition remains gated by the blocking human checkpoint precedent (01-01), exercised in 03-04. |
</threat_model>
