Create `deploy/` with two files.

**`deploy/telemetry-logger.service`** — reproduce 03-RESEARCH.md Pattern 1's unit text. The
load-bearing points, each with its reason, so a later editor does not undo them:

    - `StartLimitIntervalSec` and `StartLimitBurst` belong in the `[Unit]` section. These keys moved
      out of `[Service]` in systemd 230 (2016), and older tutorials still show the old placement.
      Putting them in `[Service]` does not fail — systemd logs that it does not recognise the key
      and carries on, so restarts are simply never rate-limited. That is strictly worse than a
      load-time error, and it is the single reason Task 2 exists.
    - `Restart=always` with that bounded rate limit: a crash mid-session must recover unattended,
      but a crash-loop must stay visible rather than being silently absorbed. This pairs with
      03-04's `waiting-for-hardware` behaviour — because the logger stays alive through an
      unpowered bus instead of exiting, the restart budget is preserved for real faults.
    - `After=network.target local-fs.target` and `Wants=network.target`. Do NOT add `After=` or
      `Requires=` on any udev-generated device unit for the neoVI hardware. The whole point of
      03-04's retry loop is that the application owns that race; encoding it at the systemd level
      would either block startup indefinitely or require guessing a device-unit name that has not
      been established and may not exist for this device class.
    - `User=telemetry` — a dedicated non-root account (ASVS V4, least privilege). Also the reason
      `shutil.disk_usage(...).free` is the honest number to threshold against: on Linux it reports
      blocks available to an unprivileged user, already excluding the root reserve.
    - `WorkingDirectory=/opt/telemetry` with `Environment=PYTHONPATH=src` and an `ExecStart` that
      runs `telemetry.logger.cli` as a module. This must match the invocation 03-01's tracer
      actually proved works, and it is what makes the config loader's repo-relative `_REPO_ROOT`
      resolution land on `/opt/telemetry/config/logger.json` without a `--config` flag.
    - Do not add `StandardOutput`/`StandardError` overrides. The default sends both streams to the
      journal, which is what makes `journalctl -u telemetry-logger` the single diagnostic the
      runbook points at — including the case 03-04 created where a config parse failure means no
      status file exists at all.
    - Do not add `TimeoutStopSec`. systemd's own default was not verified this session, and the
      logger's shutdown budget is bounded by its own join timeouts, so an unverified number here
      would be a figure with no measurement behind it. Task 2 guards the case that matters — a
      future edit introducing a stop timeout shorter than the process needs.

**`deploy/install.sh`** — reproduce 03-RESEARCH.md Pattern 2's commands, in its order:
`set -euo pipefail`; resolve the script's own directory rather than assuming a cwd; `install -m 644`
the unit into `/etc/systemd/system/`; `systemctl daemon-reload`; `systemctl enable --now`.
`install -m 644` sets the permission bits explicitly instead of trusting whatever the source file
carried through a copy — which also avoids the spurious "marked executable" warning the researcher
hit live. `daemon-reload` must precede `enable --now` because systemd caches unit definitions and
the file on disk just changed.

Three additions beyond Pattern 2, each necessary for the unit to actually start and each flagged in
a comment as an addition that Pattern 2 did not cover:
    - Create the service account idempotently if it does not exist (system account, no home, no
      login shell). `User=` in the unit names an account that must exist or the service fails at
      first start. Derive nothing: use the same literal account name the unit file uses.
    - Verify `/opt/telemetry` exists and contains `src/telemetry` and `config/logger.json`, failing
      with a clear message if not. The script installs a service; it deliberately does not copy or
      clone the repository, because where the code comes from is a deployment decision this phase
      has not been asked to make.
    - Create the archive root and the heartbeat file's parent directory and `chown` both to the
      service account. The logger runs unprivileged and must be able to write both; without this,
      first boot fails on a permission error that looks nothing like its cause.

Mark all three, plus the `/opt/telemetry` layout assumption itself, as items to confirm during the
single Pi bring-up verification 03-07 documents. Do not create a second hardware item for them.

  <action>
Create `tests/test_deploy_unit_file.py`. There is no in-repo analog for this artifact type — no
`deploy/` directory, no systemd artifact, and no INI-adjacent parser exists in this repository — so
write it from 03-RESEARCH.md's specification rather than pattern-matching a local precedent.

**`configparser` is forbidden in this file.** It cannot safely read a real unit file, and this was
proven live rather than assumed: with its default strict mode it raises on a second `After=` line,
which is completely valid and common systemd syntax; with strict mode off it "succeeds" while
silently keeping only the last value for a repeated key and discarding the rest. The second failure
is worse than the first, because a test built on it passes while accepting a unit file that has lost
half its intended targets. Write a small line-based structural checker instead:

    - Skip blank lines and lines whose first non-space character starts a comment.
    - A line wrapped in square brackets opens a section; anything else must split on the first `=`
      into a key and a value.
    - Return a mapping from section name to an ordered LIST of `(key, value)` pairs — a list, not a
      dict, so repeated keys survive. Every assertion below reads that structure.
    - Reject a `Key=Value` line that appears before any section header, and reject an unparseable
      line, with a message naming the line number.

Do not attempt semantic validation — dependency graph resolution, directive-specific type checking,
or anything that requires knowing what systemd does with a value. That is exactly what
`systemd-analyze verify` is for, it only exists on real systemd, and imitating it here would produce
a check that looks authoritative and is not.

Write the behaviour assertions first. The duplicate-key assertion runs against a synthetic snippet
defined inside the test file, not against the shipped unit — the shipped unit has one `After=` line,
so asserting duplicate preservation against it would pass vacuously and prove nothing.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| systemd (root) → logger service user | The init system starts an unprivileged process; the privilege drop happens at this boundary |
| install script (run with sudo) → `/etc/systemd/system` | A root-run script writes a file the init system will trust and execute |
| repository working tree → the deployed car | What is checked in is what runs, or the artifact has drifted from reality |
