  <action>
Extend `src/telemetry/ops/cli.py`. Do not change the exit-code contract 03-01 fixed — this task
widens the rendering only.

**A per-state table, defined once as a module-level mapping** from state name to a
`(meaning, next_action)` pair, covering exactly the names in `HEARTBEAT_STATES`. Build the mapping
so a state present in `HEARTBEAT_STATES` but absent from the table is a hard failure at import or
first render, not a silently blank line — the runbook in 03-07 generates its troubleshooting table
from the same five names and the two must not drift. Content for each:
    - `booting` — the logger has started and is loading its configuration and DBC. Expected to last
      well under a second. If it persists, the journal has the reason.
    - `waiting-for-hardware` — the logger is alive and retrying; the CAN bus is most likely not
      powered yet. This is the normal power-up sequence on this car, not a fault. It clears by
      itself when the bus comes up.
    - `capturing` — the logger is recording. Read the evidence line below it to confirm frames are
      actually moving.
    - `degraded` — still recording, but something needs attention; the detail line names what.
    - `stopped-error` — the logger stopped and did not finish cleanly. The session's archive will
      have no completion marker. The journal has the reason.

**Staleness outranks state.** Both the headline and the exit code resolve staleness first: a stale
reading renders as stale with its age and reason, then names the state it was last in, and exits 3
regardless of which state that was. Without this, a status file frozen mid-`capturing` reads as a
healthy logger forever — the exact false-negative 03-RESEARCH.md Pitfall 5 warns about, and the
whole reason the reader carries a `staleness_reason` at all.

**The evidence line.** For `capturing` (and for `degraded`, which is still recording), render one
line built from `extras`: session name, frames per second, frames captured, frames archived. This is
what makes "alive **and** capturing" answerable rather than just "alive" — a person reading
`capturing` with 0 frames/s learns something a state name alone cannot tell them. Do not convert a
zero rate into a fault state; a parked car with the bus unpowered legitimately produces none, and a
false fault trains the team to ignore the indicator.

**The clock-went-backwards message must be written for a non-author.** Say that the machine appears
to have rebooted since this file was written, so its age cannot be trusted, and that the reliable
signal in that situation is that a running logger rewrites this file within a second of starting.

**The absent-file message** names the path it looked at, says a clean stop removes the file, and
adds the asymmetry 03-04 created: if the service is running and there is no status file at all, the
configuration failed to parse before the path was known — `journalctl -u telemetry-logger` has the
reason.

Keep the two-outputs discipline exactly as it stands: stdout carries only the single `--json` line
when `--json` is passed and nothing otherwise; every human-readable line goes to stderr.

Write the behaviour assertions first against fixture status files built with the real
`write_heartbeat` and an injected `now_fn`, never a `time.sleep`.
