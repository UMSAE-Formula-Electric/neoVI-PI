  <action>
Write `docs/runbook.md`, joining `docs/power-pull-test.md` in the same directory. The audience is
explicitly a team member who did not build the system and has no prior context from planning. Assume
they know how to open a terminal and nothing else about this repository.

Open with what this covers and which requirements it satisfies (OPS-01, OPS-02, OPS-03, OPS-07), and
what it deliberately does not: automated off-car data retrieval is a later phase, so this document
covers manual retrieval only. Do not promise automation that does not exist.

Sections, in this order:

    - **First-time install on the car.** One command: the install script from 03-06, run with sudo.
      State what it does — installs the unit, reloads systemd, enables and starts the service,
      creates the service account and the directories it needs. State the prerequisite: the
      repository present at the path the unit's `WorkingDirectory` names.
    - **Starting a session.** Apply power. That is the entire procedure — no screen, no keyboard, no
      login. Say so plainly, because a reader who has operated other loggers will be looking for a
      step that is not there.
    - **Confirming it is healthy.** The `telemetry-status` command as it is actually invoked. Then a
      table of the five heartbeat states: state, what it means, what to do. Take the wording from
      what the command prints so the two cannot disagree. Call out that
      `waiting-for-hardware` is the normal power-up sequence on this car and not a fault — it
      appears because the CM4 usually finishes booting before the CAN bus is powered, and it clears
      itself.
    - **Reading the exit code.** A table whose every row begins with the code in backticks, covering
      `0`, `1`, `2`, `3`, and `4`, each with what it means for someone scripting a check.
    - **Checking remaining space.** The explicit step: run the status command and read the free-space
      and disk-band fields. What to do at each band. Name the two threshold keys in
      `config/logger.json` and say plainly that their shipped values are chosen round numbers, not
      measurements — no full-rate session's archive growth has been measured on this car yet, so
      calibrate them once a real session's size is known. State that the logger refuses to START a
      new session below the critical band but never stops a run already in progress, and that
      nothing in this system ever deletes session data.
    - **Retrieving the data.** Where sessions live, that only a session directory carrying the
      completion marker is finished, and that an interrupted session is deliberately left without
      one. Copy whole session directories. Note that automated retrieval is a later phase.
    - **When something is wrong.** Two cases a reader cannot otherwise diagnose:
      first, a service that is running with no status file at all means the configuration failed to
      parse before the file's path was known — the journal has the reason, and give the exact
      `journalctl` invocation for the unit. Second, an age figure cannot be trusted if the machine
      has rebooted since the file was written; a running logger rewrites the file within a second of
      starting, so re-run the command rather than reasoning about the number.
    - **`## Pi bring-up: the one hardware-only verification (OPS-01)`** — use this heading text; the
      coverage test asserts it. This is the single item in this phase that cannot be checked
      anywhere but on the car. Give the procedure — install, reboot with the CAN bus unpowered,
      confirm the service comes up and reports `waiting-for-hardware`; power the bus, confirm the
      state becomes `capturing` with frames moving; reboot again with the bus already powered and
      confirm it reaches `capturing` without intervention — and state what "pass" means for each
      step. In the same section, list the assumptions to confirm while the car is in front of you,
      so they never become separate hardware items: whether the SDK's device lookup returns an empty
      result or raises when the driver is present with nothing attached; whether the archive
      filesystem mounts with the rest of local storage or needs explicit ordering; the deployment
      layout, service account, and archive-root ownership 03-06 assumed. Say plainly that OPS-01
      stays Pending until this section passes, and cross-reference `docs/power-pull-test.md` as the
      precedent for a requirement held open on a physical test.
