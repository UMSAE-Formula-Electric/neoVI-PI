## Framing overhead (D-06 — computed, never implemented)

```
BATCH_HEADER_BYTES = 13     # protocol_version 1 + dict_version 1 + base timestamp 8 + frame_count 2 + batch_seq 1
CRC16_BYTES        = 2
COBS_BLOCK_BYTES   = 254

cobs_worst_case_overhead(payload_bytes: int) -> int          # payload_bytes // 254 + 1
all_in_bytes_per_batch(clean_payload_bytes: int) -> int      # header + (clean + crc) + cobs(clean + crc)
overhead_breakdown(clean_payload_bytes: int, frames_in_batch: int) -> OverheadBreakdown
```

`OverheadBreakdown` is a frozen dataclass carrying `clean_payload_bytes`, `batch_header_bytes`, `crc_bytes`, `cobs_bytes`, `all_in_bytes`, `frames_in_batch`, `clean_bytes_per_frame`, `all_in_bytes_per_frame`, `overhead_pct`. No COBS or CRC implementation is written and no `cobs` or CRC package is installed — the constants come from the already-settled architecture design and D-06 scopes this to arithmetic.

## Ablations (D-10)

```
ABLATIONS = ("full", "no_sequence_byte", "raw_payload", "no_dictionary")
ablation_options(name: str) -> EncoderOptions
```

| Ablation | `EncoderOptions` | Isolates |
|---|---|---|
| `full` | all defaults True | the headline, the encoding that ships |
| `no_sequence_byte` | `sequence_byte=False` | the per-ID sequence byte's cost, estimated at 12-15% in prior research |
| `raw_payload` | `payload_delta=False` | what the per-ID XOR delta buys |
| `no_dictionary` | `use_dictionary=False` | what the static ID dictionary buys against a raw 4-byte frame id |

Every ablation is measured with round-trip verification on, over the same materialized frame list, so every ablation figure is a figure for an encoding proven reversible on exactly the frames it counted.

## Peak windows (D-11)

```
peak_windows(timeline: Sequence[tuple[int, int]], windows_s: Sequence[float]) -> dict[str, float]
```

`timeline` is `(timestamp_us, all_in_bits)` pairs, one entry per batch, ordered. The return maps each window label (for example `"0.1s"`, `"1s"`, `"10s"`) to the maximum bits/s observed over any sliding window of that length, computed by a two-pointer sweep. A window longer than the run duration returns the whole-run average and is annotated in the report as such rather than silently reported as a peak.

Peaks are resolved at **batch granularity**, because all-in bytes are a per-batch quantity. The report records `peak_window_granularity: "batch"` and the batch period in microseconds so a reader knows the resolution of the number they are reading. Do not interpolate below batch resolution and do not report a theoretical worst-case frame alignment — D-11 rules both out.

## Report document shape

`build_report` returns a plain dict with two top-level keys.

`meta` carries: `generated_at`, `dbc_path`, `dbc_message_count`, `dict_version`, `config_hash`, `seed`, `duration_s`, `batch_frames`, `worst_n`, `peak_windows_s`, `bus_assignment_confirmed`, `bus_targets`, `achieved_bus_fps`, `thresholds` (echoed from gate.json), `input_provenance`, and `known_limitation`.

- `input_provenance` states in plain words that the measured stream is synthesized from `epbr2026_DBC_v1.0.dbc` per D-01 and is not a captured vehicle log.
- `known_limitation` states that payload entropy is the quantity this gate exists to measure and that synthetic data has only the entropy the model gives it, naming the three-bracket band and the worst-case Phase 1 re-check as the compensating controls.

`brackets` maps each of `best` / `typical` / `worst` to: `aggregate` (frame count, clean bytes, clean bytes/frame, all-in bytes/frame, average kbit/s clean and all-in), `per_id` (a list of `PerIdStats`), `categories` (a dict whose keys are exactly `CATEGORIES`, empty buckets included with a `note` naming the detection method), `worst_n` (the top `worst_n` IDs by clean bytes/frame, descending, computed independently of the categorical buckets), `ablations` (a dict keyed by `ABLATIONS`, each with bytes/frame, kbit/s, `delta_pct_vs_full`, and `roundtrip_verified`), and `peaks` (the `peak_windows` result plus the granularity note).

`meta.threshold_comparison` states, per pre-registered threshold in `gate.json`, the measured value, the threshold value, the headroom percentage, and a boolean `within_threshold`. It does **not** emit a verdict string. The go/no-go is a human document — D-16 is explicit that SC-4 wants a decision every later phase is built against, and that is a document, not a tool output.

## CSV

`write_report_csv` emits one row per `(bracket, frame_id, is_extended)` with columns: `bracket`, `frame_id_hex`, `is_extended`, `message_name`, `sender`, `bus`, `rate_source`, `rate_hz`, `categories`, `frame_count`, `clean_bytes_per_frame`, `all_in_bytes_per_frame`, `kbps_all_in`. Written with the stdlib `csv` writer using `newline=""`, matching the convention in `src/new_logger.py`.

**Flagged assumptions:**
- **Peak resolution.** All-in bytes are a per-batch quantity, so sliding-window peaks resolve at batch granularity, not per frame. At 100 frames per batch and ~4,000 frames/s that is roughly 25 ms, which is coarser than the 100 ms window it is used to compute. The report records the granularity so the number is read for what it is; a finer peak would require implementing framing, which D-06 puts out of scope.
- **Assumption A3 — batch size.** The all-in figure and therefore every bit-rate comparison depend on the single batch size stated in `gate.json`. The report emits the formula alongside the number so a different Phase 1 batch size can be recomputed rather than re-measured.
